## 0. 全機能共通・横断テストケース（ファイル自体の異常系）

以下は「PDF↔Office変換」「OCR」「電子署名」「パスワード保護」すべての入力元PDF/Officeファイルに対して共通で試すべきケース。

| # | シナリオ | 入力条件 | 期待挙動 | コード上の根拠・懸念 |
|---|---|---|---|---|
| 0-1 | 0バイトファイル | サイズ0のダミー`.pdf`/`.docx`を選択 | `PDFDocument(url:)`が`nil`または`pageCount == 0`を返し、`invalidInput`/`emptyDocumentSet`系エラーを画面に表示。クラッシュしない | `PDFService`各関数は`guard let ... , pageCount > 0`で防御済み。Office側は`OOXMLZipReader`がZIPとして解析不能な場合に例外化される想定 → **要実機確認** |
| 0-2 | 拡張子偽装ファイル | `.pdf`拡張子だがテキストファイルの中身／`.jpg`を`.pdf`にリネーム | `invalidInput`として弾かれる（`PDFDocument`初期化失敗） | 拡張子ではなくファイル内容で判定しているため理論上は安全。**実機で意図的にリネームしたファイルを用意して確認** |
| 0-3 | 破損PDF（ヘッダのみ有効・本体切断） | ダウンロード中断を模した途中切れファイル | クラッシュせず`invalidInput`表示 | PDFKitのパース失敗時の挙動はOS/iOSバージョン依存の可能性あり。iOS 17系実機での確認必須 |
| 0-4 | パスワード付きPDFを非対応機能に投入 | 暗号化PDFを「結合」「圧縮」「透かし」等（パスワード解除を経ない機能）に入力 | OCR/Office変換は明示的に`passwordProtectedFile`エラーで弾く実装あり。**一方でmerge/compress/split/watermark/pageEditにはロック判定がない**ため、`PDFDocument(url:)`はロック状態でも非nilを返し得る → 空PDFとして処理されたり、意図しない出力になる可能性 | `mergePDFs`/`compressPDF`/`splitPDF`/`addWatermark`/`generateEditedPDF`に`document.isLocked`チェックが**ない**。**要修正候補**として開発チームへ共有推奨 |
| 0-5 | 巨大ファイル（1GB超） | 1GB/2GB程度の高解像度スキャンPDFや大量ページPDF | OCR・Office変換は`fileTooLarge`（上限100MB）で明示的に拒否される。**一方でmerge/compress/split/watermark/pageEdit/protect/署名には`checkFileSize`によるサイズ上限チェックが実装されていない** | `PDFService.maxInputFileSizeBytes = 100_000_000`は`convertToOffice`/`convertOfficeToPDF`のみで呼ばれている。他機能は無制限にメモリへロード・`UIGraphicsPDFRenderer`でレンダリングするため、**実機での高メモリ負荷時にOSにより強制終了（Jetsam）されるリスクが高い**。実機検証の最優先項目 |
| 0-6 | 1ページのみ・極端に大きいページサイズ | A0サイズや極端な`mediaBox`を持つPDF1ページ | 各種レンダリングが極端に遅くならないか、メモリスパイクが起きないか | `renderPageImage`は`pageRect.size`をそのままビットマップ化するため、巨大`mediaBox`だとメモリを大量消費 |
| 0-7 | 大量ページ数（1000ページ超） | ページ数の多いPDF | 結合・分割・圧縮・OCR（進捗表示`onProgress`あり）が実用時間内に終わるか、UIがフリーズしないか | OCRは`actor`化されておりメインスレッドをブロックしない設計だが、体感速度は実機で要確認 |
| 0-8 | ファイル名に特殊文字・絵文字・非常に長い名前 | `🔥報告書(最終)_v2　最終版.pdf`等 | 出力ファイル名/共有シートで文字化け・クラッシュしないこと | UIDocumentPickerView経由のURLはサンドボックス内一時パスのため影響小だが、共有（`ActivityView`）時の表示名は要確認 |
| 0-9 | iCloud Drive上のオンデマンドダウンロード未完了ファイル | 端末にダウンロード済みでない（雲アイコン付き）ファイルを選択 | ダウンロード待ちのハンドリング、またはタイムアウト時のエラーメッセージ表示 | `DocumentPickerView`のセキュリティスコープ・ダウンロード完了待ちの実装有無を要確認。未完了のまま`Data(contentsOf:)`を呼ぶと空データ/エラーになり得る |
| 0-10 | ファイルアクセス権限喪失（他アプリ共有フォルダの権限失効） | Files appの外部プロバイダ（Google Drive等）でアクセス権が切れたファイル | セキュリティスコープ付きURLの`startAccessingSecurityScopedResource`失敗時に適切なエラー表示 | 実装箇所（`DocumentPickerView`）を確認し、権限取得失敗パスのエラーメッセージが実装されているか要チェック |

## 1. PDF↔Office双方向変換（`convertToOffice` / `convertOfficeToPDF`）

### 1-A. PDF → Office

| # | シナリオ | 期待挙動 |
|---|---|---|
| 1-A-1 | パスワード保護PDFをOffice変換に投入 | `passwordProtectedFile`エラーで、「パスワード設定機能で解除してから」という案内文が表示される（実装済み） |
| 1-A-2 | 100MB超のPDFをOffice変換に投入 | `fileTooLarge`エラー、上限MB数がメッセージに表示される（実装済み） |
| 1-A-3 | 文字情報を持たない画像スキャンPDF（テキストレイヤーなし）をWord変換 | `document.page(at:)?.string`が空文字になるため、**中身が空のdocxが生成される**（バリデーションなし）。ユーザーが「変換したのに文字が入っていない」と誤解する可能性 → OCR未実施の画像PDFをWord変換した場合の警告UIを検討すべき |
| 1-A-4 | 表・罫線が複雑なPDFをExcel変換 | `extractTableRows`は文字の座標（空白幅・X座標の隙間）で列を推定するヒューリスティクスのため、**罫線のみで区切られ空白のない表**や、**セル内で改行された表**では列がずれる／行がまとまらない。意地悪ケースとして「セル結合を含む複雑な表」「日本語全角スペース区切りの表」を用意し崩れ方を確認 |
| 1-A-5 | 極端に列数が多い表（20列超）をExcel変換 | `renderExcelPDF`は列幅を40〜150ptにクランプするのみで用紙幅（792pt）を超えた場合の折り返しがないため、**右側の列が用紙外にはみ出して読めなくなる** |
| 1-A-6 | 1ページのみ・PowerPoint変換 | ページ画像として1枚のPNGスライドが生成されることを確認（`slides`が空の場合`officeConversionFailed`） |
| 1-A-7 | 縦横混在（ページごとに向きが異なる）PDFをPowerPoint変換 | 各ページの`renderPageImage`結果をそのまま画像化するため向きは保持されるはずだが、スライドサイズ（1枚目基準）と縦横比が合わない場合の見え方を確認 |
| 1-A-8 | 出力先ディレクトリが書き込み不可 | `officeConversionFailed`で握りつぶさずエラー内容が伝わるか（`do/catch`で`officeConversionFailed`に丸められる実装のため詳細原因はログでしか追えない点に注意） |

### 1-B. Office → PDF

| # | シナリオ | 期待挙動 |
|---|---|---|
| 1-B-1 | マクロ有効Office形式（`.docm`/`.xlsm`/`.pptm`） | 拡張子/フォーマット判定がZIP構造ベースであれば読める可能性はあるが、**マクロを実行しない**ことをコードレビューで再確認（`OfficeDocumentReader`系がXMLテキスト抽出のみで外部エンティティやマクロを評価しないか） |
| 1-B-2 | パスワード保護されたOfficeファイル（暗号化docx/xlsx） | 暗号化OOXMLはZIP構造自体が通常と異なる（`EncryptedPackage`ストリーム）ため、`OOXMLZipReader`が読めず`officeConversionFailed`または`invalidInput`になる想定。**エラーメッセージが「パスワード保護されています」等の的確な文言になっていない可能性**（現状`readOffice`は例外を一律`officeConversionFailed`に丸めており原因種別を区別しない） → メッセージ改善候補 |
| 1-B-3 | 破損したZIP構造のdocx（中身のXMLだけ壊れている） | `readOffice`のcatchで`officeConversionFailed`に丸められクラッシュしないことを確認 |
| 1-B-4 | 悪意あるZIP（Zip Bomb / パストラバーサルを含むエントリ名 `../../etc/passwd`） | **セキュリティ観点で最重要**。`OOXMLZipReader`の展開処理が①展開後サイズに上限を設けているか（Zip Bomb対策）、②エントリパスのサニタイズをしているか（パストラバーサル対策）をコードレビューし、確認できない場合は展開先が常にメモリ上/サンドボックス内のみであることを実機・コードの双方で確認 |
| 1-B-5 | 2000ページを超える大容量Wordドキュメント | `renderPDF`は`maxPageCount = 2000`で打ち切る安全弁があるため、無限ループやOOMには陥らない設計。2000ページ超の文書で「途中で切れる」ことをユーザーに通知しているか（現状打ち切りは無言）→ **通知なしで切れるのはユーザー体験上の問題、要検討** |
| 1-B-6 | 空のExcelブック（シートはあるがセルデータなし） | `sheets`が空配列のシートで`renderExcelPDF`がクラッシュしないか（列数`max(...,1)`で0除算回避済み） |
| 1-B-7 | 画像を含むPowerPoint（非対応の画像形式・EMF/WMF等） | `UIImage(data:)`が`nil`を返す画像は`compactMap`でスキップされる → 該当スライドの画像だけ無言で消える。ユーザーへの警告有無を確認 |
| 1-B-8 | 拡張子とバイナリ内容の不一致（実体はxlsxだが`.pptx`として選択） | フォーマット指定は呼び出し側UIのpicker選択に依存するため、**ユーザーが誤ったフォーマットを選んだ場合に分かりやすいエラーになっているか**を確認 |

## 3. 電子署名（`SignatureService.addSignature`）

> **監査上の重要な前提**: 本機能は指描画した署名画像をPDFページ上に画像として合成する機能であり、**PDF標準の暗号学的デジタル署名（証明書ベース／改ざん検知可能な`/Sig`フィールド）ではない**。法的な電子署名（電子署名法・eIDAS等）が要求される用途には利用できない。UI文言・ストア説明文が「電子署名」と表記されている場合、**ユーザーが暗号学的な署名機能だと誤解しないよう文言の明確化を検討**（セキュリティ監査観点での指摘事項）。

| # | シナリオ | 期待挙動 |
|---|---|---|
| 3-1 | ページ範囲外のインデックスを指定 | `invalidPageIndex`で弾かれる（実装済み） |
| 3-2 | 0ページのPDFに署名 | `invalidInput`で弾かれる（実装済み） |
| 3-3 | 署名画像が透明背景でない／背景が白いままキャンバスから書き出された場合 | 元のPDF内容の上に不透明な白背景で重なり、下の文字が隠れてしまわないか（`signatureImage.draw(in: rect)`は単純な描画で透過合成の前提。PencilKit側の書き出し形式を要確認） |
| 3-4 | `rect`がページ範囲外・負の値・ゼロサイズ | クラッシュしないこと（UIKitの`draw(in:)`は範囲外矩形でも通常クラッシュしないが、意図しない位置に描画されないかUI側の入力検証を確認） |
| 3-5 | 極端に小さい/大きい署名画像を極端に小さい/大きい`rect`に描画 | 引き伸ばしすぎで判読不能にならないか、UI側で許容範囲を制限しているか |
| 3-6 | パスワード保護PDFに署名 | 現状ロック判定なし（0-4参照）。ロックされたPDFに対して`PDFDocument(url:)`がどう振る舞うかを実機で確認し、意図しない空PDF/破損出力にならないか検証 |
| 3-7 | 同一PDFに複数回連続で署名を追加 | 署名の重ね書き・出力ファイルサイズの肥大化（毎回全ページ再描画するため、多重変換でPDF品質が劣化しないか） |
| 3-8 | 署名後にファイル改ざん検知ができるか（意図的にPDFバイナリを書き換えて再度開く） | 暗号学的な署名ではないため改ざんを検知できないのは仕様。**「署名済みPDFは改ざんされていないことが保証される」という誤解を招く表現がないか**、UI/マーケティング文言を確認する監査項目 |

## 4. パスワード保護（`protectPDF` / `unlockPDF`）

| # | シナリオ | 期待挙動 |
|---|---|---|
| 4-1 | 空文字パスワードで保護を実行 | `invalidInput`で弾かれる（実装済み） |
| 4-2 | 誤ったパスワードで解除 | `incorrectPassword`エラー（実装済み） |
| 4-3 | 非ASCII文字（絵文字・日本語・結合文字）をパスワードに使用 | PDFKitの暗号化仕様（RC4/AESのリビジョン）によって非ASCII文字の扱いが変わる可能性。**保護→解除のラウンドトリップが日本語パスワードでも成立するか**を実機で確認（既存ユニットテストはASCIIパスワードのみと推測されるため要確認） |
| 4-4 | 極端に長いパスワード（1000文字超） | クラッシュ・タイムアウトしないこと |
| 4-5 | ユーザーパスワードとオーナーパスワードを分離した場合の挙動 | 現状の実装は`userPasswordOption`と`ownerPasswordOption`に**同一の`password`を設定**している。将来「閲覧用パスワード」と「編集制限用パスワード」を別々に設定するUIを追加する場合の設計制約として記録（現状は意図的な仕様か要確認） |
| 4-6 | 既にパスワード保護されているPDFに再度`protectPDF`を実行 | 二重保護時の挙動（上書きされるか、失敗するか）を確認 |
| 4-7 | ロックされていないPDFに`unlockPDF`を実行 | `document.isLocked`が`false`のため即座にページ移し替えのみ行われ正常終了する想定。エラーにならないことを確認（仕様通り） |
| 4-8 | 暗号化アルゴリズムの妥当性確認（セキュリティ監査） | PDFKitの`write(to:withOptions:)`が既定でどの暗号化強度（40bit RC4 / 128bit RC4 / AES-128 / AES-256）を採用するかを`PDFDocumentWriteOption`のドキュメントで確認し、**旧式の弱い暗号化（40bit RC4等）がデフォルトで使われていないか**を明示的にテスト・記録する。ストア説明文で「パスワード保護」を強く訴求している以上、暗号強度の裏付けは監査上必須 |
| 4-9 | パスワード保護PDFを機種変更・iCloudバックアップ経由で復元した場合 | ファイル自体はサンドボックス内保存のため通常のバックアップ機構に依存。復元後も同じパスワードで開けることを確認 |

## テスト用ファイル準備の指針

- **0バイトファイル**: `touch empty.pdf`
- **破損PDF**: 正常なPDFの先頭50%だけを`dd`等で切り出す
- **1GB超PDF**: 300dpi以上の高解像度画像を数百ページ結合して作成、またはダミーデータで水増し
- **パスワード付きOffice**: Microsoft Word/Excel/PowerPointで「読み取りパスワード」設定して保存したファイル
- **Zip Bomb相当のdocx**: 通常のdocxのZIPエントリを巨大な繰り返しデータに差し替えたテスト専用ファイル（**取り扱い注意・テスト環境のみで使用し配布しないこと**）
- **多言語PDF**: 中国語簡体字・韓国語・アラビア語のサンプル文書（著作権フリーのものを使用）

> これらのテストファイルはリポジトリの`SampleFiles/`に倣い、`SampleFiles/qa-edge-cases/`のようなサブディレクトリを別途用意し、`.gitignore`で大容量ファイルを除外することを推奨する。
